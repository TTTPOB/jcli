# ADR 0004：Claude Code 工具批末配对同步

状态：提议中，待审阅。

## 背景

j-cli 管理 py:percent 与 notebook 的配对关系。编辑前的漂移检查可能执行同步，编辑后的流程再将修改同步到 notebook。连续小编辑如果逐次执行这两项流程，会重复启动进程、读写 notebook；只合并后置流程，下一次编辑的前置检查仍可能同步上一轮修改。

[ADR 0003](<0003-batched-pair-synchronization.md>) 定义了按编辑段合并同步的方向。本提案单独规定 Claude Code 的接入边界，不依赖其他宿主的常驻插件或父子工具调用关系。

Claude Code 官方提供 `PostToolBatch`：一批工具全部完成后触发一次，发生在下一次模型请求之前。这个边界适合批内合并，但不代表一个用户请求里的所有编辑已经结束。连续编辑如果分属多个模型工具批次，仍会分别同步。

## 决策

**按 Claude Code 工具批次合并同步。每个配对在一批中的首次编辑前检查，批末同步一次；需要在批内消费 notebook 时，必须先结束相关编辑段并完成同步。**

采用现有同步 command hooks，由 j-cli 适配层处理状态和去重，不修改 Claude Code 平台。不将昂贵同步改成异步后台任务，不新增服务或持久任务队列。

### 1. 编辑前后的职责

1. `PreToolUse` 匹配编辑工具：首次编辑某个配对时执行现有前置检查；检查成功后记录该配对已准入。
2. 本段后续编辑同一配对跳过重复配对检查，同时保留直接编辑 notebook 的拒绝规则、无配对文件的快速跳过及宿主自身权限检查。
3. `PostToolUse` 只记录成功编辑产生的待同步配对，不逐次执行昂贵同步。
4. `PostToolBatch` 对本批涉及的配对去重，等待后置同步完成，再清除该批状态。即使一批只包含一个编辑，也经过同一收尾流程。

配对键由工具工作目录与文件路径规范化得到，并将对应 Python 文件和 notebook 归为同一配对。`PostToolBatch` 没有 matcher，适配层在处理输入时筛选相关工具。

前置准入记录也保留到批末：工具报错不一定意味着文件没有变化，批末对已准入但结果不明的配对执行现有检查或同步，而不是仅依赖成功事件。具体检查必须沿用现有冲突处理语义，不能无条件用一侧覆盖另一侧。

### 2. 跨 hook 的最小状态

command hooks 是独立进程，不能使用普通进程内变量共享状态。适配层需要会话期临时记录，按 `session_id` 和可选 `agent_id` 隔离，保存每个配对的准入、待同步及失败状态。`tool_use_id` 用于关联单次调用，不作为批次标识。

官方输入未提供本方案可依赖的批次 ID 或 root-tool ID。状态以正常 `PostToolBatch` 收尾为边界，不根据 transcript 的写入时机推算批末。并发 hook 可能同时检查同一配对，适配层应使用简短的配对级互斥保护首次检查和状态更新，避免真实可发生的重复检查；不引入通用调度器。

这些记录是临时协调数据，不是重启后自动重放的任务队列。异常退出后由现有漂移检查恢复，不能让遗留的“已检查”标志使新一轮编辑跳过首次检查。实施前必须验证目标版本中主代理、子代理及异常收尾的隔离和生命周期足以支撑这一状态模型。

### 3. 同步与消费边界

| 操作或边界 | 行为 |
| --- | --- |
| 同段再次编辑同一 Python 文件 | 复用首次检查，记录修改 |
| 读取已修改的 Python 文件 | 直接读取，不必同步 notebook |
| 读取对应 notebook 或配对输出 | 同步相关待同步配对后再读取 |
| Bash／PowerShell 或 j-cli 执行工具 | 同步当前 agent 的待同步配对后再执行 |
| `PostToolBatch` | 等待本批剩余同步完成，在下一模型请求前收尾 |
| 正常 `Stop`／`SubagentStop` | 对未收尾状态作兜底检查和同步 |

消费屏障由同步 `PreToolUse` handler 执行，匹配实际读取与执行工具。首期 shell 统一作为消费边界，不分析复杂命令是否访问 notebook。同步完成后结束相应编辑段；之后再次编辑需重新检查。

例如，一批包含多个编辑且没有依赖消费者时，每个配对执行一次前置检查和一次批末同步。“编辑 → 执行 notebook → 编辑”的有序流程在执行前必须已同步，后续编辑重新检查；若这些操作分属不同工具批次，各批照常收尾。只有目标平台确实提供批内有序执行时，才将同样的分段规则用于批内操作，本提案不假定存在这种接口。

**同步 hook 只能等待已经发生的修改，不能为同一并行批次中尚未完成的写入建立依赖顺序。** 若 notebook 消费与其依赖的编辑并行提交，消费前 hook 可能先于编辑完成，批末同步也晚于消费。首期不承诺支持这种依赖关系；它们必须使用有序调用或分成不同工具批次。部署验证必须确认实际工作流满足此条件，不能以配置了 `PreToolUse` 为由宣称任意批内读写都一致。

Claude Code 外部的 Jupyter UI、终端命令以及程序自行进行的文件访问不经过这些工具 hook。批内 UI 可能看到旧 notebook；外部命令若要求读取最新内容，需要自身经过 j-cli 的同步入口。提示中的 `@` 文件引用也不触发 `Read` 的前置 hook，不能依赖它建立消费屏障。

### 程序化调用的限制

本方案依赖 Claude Code 实际交付的工具 hook，不将任意脚本或外部工具包装器视为可识别的编辑批次。仅在嵌套编辑和读取也触发这些 hook 时，才能登记修改并在读取前同步；没有这一保证的包装器不在支持范围内。

例如，脚本内“编辑 → 编辑 → 读取 notebook → 编辑”需要在中间读取前同步。只在外层工具完成后同步不足以保证该读取正确。脚本直接通过文件 API 或子进程读写文件，不会自动触发对应编辑／读取 hook，不能依赖本方案及时更新 notebook。

消费前同步是待新增能力，必须与延迟同步一起实现。可观察的、有序嵌套调用与同批并行工具仍需分别验证；不以外层存在批末通知推断内部调用也已被拦截。

## 失败与取消

- 首次检查失败时，不准入该次编辑。
- 消费前同步失败时，通过 `PreToolUse` 的拒绝结果阻止依赖操作，报告未同步的配对和原因。
- 批末同步失败时，报告“Python 已修改，notebook 未完成同步”，保留失败状态；用 `PostToolBatch` 的停止控制避免自动进入下一模型请求。后续相关操作必须先处理该失败，不能将其视为同步成功。
- 原工具报错时保留原始诊断，并尝试对已准入配对收尾；同步失败作为额外诊断，不覆盖原错误。
- `Stop` 不覆盖用户中断，API 错误使用 `StopFailure`。收尾 hook 只能提供有界补救，不能保证强制退出时完成同步。异常后重新编辑必须执行首次漂移检查；不能依赖 `SessionEnd` 独自承担所有恢复。

目标版本对取消时是否触发 `PostToolBatch`、失败调用在批输入中的形态及 hook 超时的行为，须通过聚焦测试确认。未得到保证的路径按“可能未同步”处理，不设计无限重试。

## 实现范围与替代方案

实施范围是 j-cli 的 Claude Code hook 适配层、setup 生成流程及相应测试，配对判断、漂移处理、输出保留与同步本身继续使用现有实现。需要同时替换原有逐次前置／后置策略；只新增批末 hook 会留下原有重复同步。

非目标（No-go）：不跨模型工具批次积累修改。跨批次状态维护及异常恢复会显著增加复杂度，目前没有明确收益。批末是本方案确定的同步边界，不将跨批次合并列为后续阶段。

| 方案 | 取舍 |
| --- | --- |
| 本提案：批末去重并合并前置检查 | 边界确定，状态短；无法合并多个工具批次 |
| 只将后置同步移到批末 | 前置检查仍可能逐 edit 同步，收益不足 |
| `async: true` 或定时防抖 | async 每次 hook 仍单独启动进程；定时防抖需要另建归集逻辑。两者均不自带消费前完成屏障，不作为本方案 |

## 验收条件

使用真实配对文件和目标 Claude Code hook 执行链验证，执行端可用替身，不依赖远端服务器。

1. **次数与分段**：同批同配对多次编辑只有一次前置检查和一次批末同步；不同配对独立去重；分属两批的编辑分别同步。消费后再编辑正确重新分段。
2. **数据正确性**：同步后的 notebook 源码、cell ID 及需保留的输出正确；无配对文件快速跳过，直接编辑 notebook 的既有规则保持。
3. **消费时序**：读取 Python 不增加同步；有序读取 notebook、读取配对输出及执行 shell／j-cli 时，在消费者启动前完成同步；明确验证同批并行依赖不在支持范围。
4. **并发与隔离**：同配对并发 hook 不重复首次检查；主代理与子代理不会互相清除待同步状态；临时状态不会使新批或恢复后的编辑错误跳过检查。
5. **失败恢复**：检查失败阻止编辑，消费前同步失败阻止消费，批末失败停止后续自动模型处理并报告路径；工具失败、用户中断和强制退出后的再次检查能发现未同步状态。
6. **收益**：对代表性 notebook 比较逐次策略与批末策略的进程数、前后置流程次数和整段耗时，同时记录每批编辑数量。以减少重复工作为目标，不承诺固定提速倍数。

## 审阅与部署条件

应先核实目标平台最新版本能力与输入 schema，更新版本依据，重点确认 `PostToolBatch` 可用性、失败／取消收尾、并发 hook 顺序及子代理身份字段。依据复核结果确认是否实施；决定实施后，将状态更新为“已接受”，再开始实现。

部署前需要通过上述验收，确认现有集成中逐 edit 同步入口已被替换，并通过项目既有 setup 流程生成 hook 配置和重新加载平台。不手工修改安装副本或生成产物。若目标版本不能提供所需批末事件，暂停部署本方案，不静默退化为定时或异步同步。

## 官方依据与调查基线

调查基线为本提案编写时读取的 Claude Code 官方在线 hooks reference；未取得 `PostToolBatch` 首次支持版本的可靠官方依据，因此不声明最低版本，也不将在线文档内容视为已安装版本的保证。接受提案前应补入目标版本及复核结果。

- [工具生命周期与批末事件](https://code.claude.com/docs/en/hooks#posttoolbatch)：`PostToolUse` 每个工具调用触发一次；`PostToolBatch` 在整批 resolve 后、下一模型请求前触发一次，输入为 `tool_calls`。
- [公共输入字段](https://code.claude.com/docs/en/hooks#common-input-fields)：会话与代理身份；transcript 异步写入，不适合作为完成屏障。
- [工具执行前 hook](https://code.claude.com/docs/en/hooks#pretooluse)：消费前等待及拒绝机制；`@` 引用不触发该事件。
- [工具执行后 hook](https://code.claude.com/docs/en/hooks#posttooluse)：成功工具结果与路径输入；执行后反馈不能撤销已经完成的写入。
- [正常回合结束](https://code.claude.com/docs/en/hooks#stop)：`Stop` 的触发范围及用户中断例外。
- [后台 hook](https://code.claude.com/docs/en/hooks#run-hooks-in-the-background)：默认同步等待；异步执行每次创建独立后台进程，不能提供本方案的合并与消费屏障。
