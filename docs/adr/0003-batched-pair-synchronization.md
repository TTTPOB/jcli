# ADR 0003：按编辑段合并配对同步

状态：提议中，待审阅。

## 背景

j-cli 通过编辑前后的配对检查管理 py:percent 与 notebook。前置流程检查漂移并在必要时同步，后置流程将编辑结果同步到 notebook。每次编辑独立运行这两项流程，会重复支付进程启动和 notebook 读写成本。notebook 包含较大图像输出时，即使只修改一行注释，同步也需要处理整个文件。

例如，对同一个 Python 文件连续执行 20 次小编辑，现有策略会执行 20 次前置流程和 20 次后置流程。如果这些修改之间不读取或执行 notebook，只需首次确认配对状态，并在修改完成后同步一次。

[ADR 0001](<0001-lightweight-pair-guards.md>) 已通过轻量入口跳过无配对文件的检查。本提案进一步减少有配对文件的连续编辑所产生的重复同步。

## 决策

**按编辑段合并同一配对文件的同步：首次编辑前检查，连续编辑期间登记待同步，在读取配对内容、执行代码或批次结束前完成同步。**

第一阶段修改 j-cli 的 DSH 插件，同时覆盖：

- 同一 assistant 消息中的多个原生编辑调用。
- PTC（程序化工具调用）中通过 `tools.*` 发出的顺序或并发提交的编辑调用。

使用 DSH 现有的调用身份、步骤生命周期和可等待的工具执行接口，不修改 DSH 宿主源码。其他平台后续分别接入自己的生命周期接口。

### 1. 编辑段

编辑段指同一工具批次或 PTC 程序中，对某个配对文件进行的一组修改，终止于以下任一边界：

- 需要读取或执行配对 notebook。
- 工具批次或 PTC 程序结束。

一个批次可以包含多个配对文件和多个编辑段。纯读取已修改的 Python 文件不需要结束编辑段，因为修改已写入该文件。

常驻插件按当前 agent 和批次保存状态，记录每个配对是否已完成首次检查、是否发生实际写入及后置同步所需参数。配对键使用按工具工作目录解析的绝对路径，避免同一文件因路径写法不同而重复同步。PTC 利用宿主提供的父子调用关系，原生调用按所在步骤归集。

### 2. 合并前置与后置流程

1. 首次编辑某个配对，运行现有前置检查，处理已有漂移。
2. 本段后续编辑同一配对，跳过重复的配对检查与同步，保留其他宿主权限和工具检查。
3. 实际写入后，将该配对标记为待同步，不逐次启动后置同步。
4. 到达同步边界，等待每个待同步配对完成现有后置流程，再清除本段状态。

前置流程本身也可能同步，因此必须同时合并前置与后置流程，才能避免下一次编辑前重复处理上一轮修改。

直接编辑 notebook 的拒绝规则、无配对文件的快速跳过及现有冲突处理语义继续保留。是否发生写入以文件工具的实际写入通知为依据，不只根据最终工具结果是否成功判断。

### 3. 同步边界

| 后续操作 | 行为 |
| --- | --- |
| 再次编辑同一 Python 文件 | 继续本段 |
| 读取已编辑的 Python 文件 | 直接读取，继续本段 |
| 读取对应 notebook 或配对输出 | 先同步相关配对，再读取 |
| 执行 Bash／shell 工具 | 先同步当前批次待同步配对，再执行已有检查和命令 |
| PTC 程序结束 | 等待剩余配对同步完成，再返回外层工具结果 |
| 原生工具批次结束 | 登记剩余同步任务，在下一模型步骤或正常回合结束前等待完成 |

首期对 shell 使用统一同步边界，不分析复杂命令是否访问 notebook。没有待同步文件时立即返回。

例如：

```text
编辑 → 编辑 → 读取 Python → 编辑 → 批次结束
首次检查一次；批末同步一次。

编辑 → 执行 notebook → 编辑 → 批次结束
执行前同步一次；后续编辑重新检查，批末再同步一次。
```

PTC 中使用 `Promise.all` 提交编辑仍遵循宿主的写工具串行调度规则，采用与顺序提交相同的合并策略。

### 4. 结束、失败与取消

PTC 在外层可等待的执行收尾中同步，宿主先排空子调用，插件再等待剩余同步任务。原生批量在步骤结束时登记同步任务，并在下一步骤准入及正常回合收尾时等待；批内读取或执行工具也必须等待正在进行的同步。

消费前同步失败时，不启动依赖该结果的工具，返回明确诊断。收尾同步失败时，明确报告“Python 已修改，notebook 未完成同步”，同时保留原程序错误。

文件写入后即使程序报错或被取消，仍尝试有界收尾。取消后的清理使用独立超时，不能复用已取消的执行信号，也不继续启动编辑或其他业务工具。原生调用取消后，宿主可能显示空闲而清理尚未完成；插件追踪清理任务，在下一次相关操作前等待，并在卸载时等待有界清理。

进程强制退出不保证清理完成，下一次首次检查仍负责发现漂移。首期不新增持久队列。

### 5. 实现范围

同步继续复用现有 Python guard。每个不同配对执行一次后置流程，传递对应编辑的路径和参数；归集状态保存在常驻插件内，不新增服务或多文件批量 CLI。

首期不改变图像格式、输出保留策略或同步器内部全量读写方式。这些优化可以独立进行。

## 一致性取舍

编辑段内，Python 文件已经写入，notebook 可以暂时保留旧内容。Jupyter UI 或其他外部读取者因此可能看到尚未同步的 notebook；正常批次结束后，进入下一模型步骤或结束回合前应已完成同步。PTC 正常返回时应已完成同步。

### 程序化调用的限制

读取／执行前同步是本提案需要新增的拦截，当前插件仅在每次编辑后立即同步。延迟编辑同步与新增消费前拦截必须一起实现。

PTC 中的“编辑 → 编辑 → 读取 notebook → 编辑”必须在中间读取前同步，不能只等程序结束。通过 `tools.read`、配对输出读取或 shell 工具消费时，插件可等待同步后放行。程序必须等待依赖的编辑完成后再提交读取；把编辑和依赖它的读取同时放入 `Promise.all` 不建立执行顺序。

直接使用 Node filesystem 或 child_process 会绕过工具执行接口，首期不透明拦截这些访问；程序需要消费最新 notebook 时应经由工具调用。通过这些 API 直接写文件也不保证进入待同步登记。

本提案不调整同步器与执行检查的源码等价规则。格式规范化与执行校验之间的兼容性应由独立回归测试保证。

## 其他平台的接入方向

| 平台 | 现有能力 | 后续适配方向 |
| --- | --- | --- |
| Claude Code | 提供整批工具完成后的 hook | 批末按配对路径去重同步；批内依赖读取仍需提前同步 |
| Codex | 提供可等待的工具前后及回合结束 hook | 编辑后登记，在消费前及回合末同步；不假定存在公开的根调用结束接口 |
| OpenCode | 提供可等待的工具前后 hook；实验性 Code Mode 有外层执行边界 | 普通调用按编辑段合并，Code Mode 利用外层结束边界 |

这些平台不自动合并 j-cli 同步，需要各自的适配层。异步 hook 只改变等待方式，不提供去重和消费前一致性。第一阶段不引入统一的跨平台持久状态协议。

## 替代方案

| 方案 | 取舍 |
| --- | --- |
| 要求模型把所有修改合成一次编辑 | 有助于减少调用，但无法保证所有编辑都以这种形式提交 |
| 只延迟后置同步 | 下一次前置流程仍可能同步，不能有效消除重复工作 |
| 异步执行或定时防抖 | 缺少确定的完成边界，仍需消费前等待和任务去重 |
| 提高超时 | 能减少超时失败，不能减少重复工作 |
| 禁用自动同步 | 需要用户或模型额外维护配对状态，损失现有工作流能力 |
| 新增 DSH 批末接口 | 现有接口足以覆盖本提案；如需让取消后的宿主空闲状态也严格等待清理，再另行评估 |

## 验收条件

使用真实配对文件和宿主执行链测试；kernel 使用替身，不依赖远端服务器或科研 notebook。

1. **调用次数**：同一消息中的多个原生编辑，以及 PTC 中顺序或 `Promise.all` 提交的多个编辑，同一配对每段仅执行一次前置和一次后置流程。
2. **最终状态**：notebook 源码、cell ID 和需保留的输出正确；不同配对独立处理，同一路径的不同相对写法只归集一次。
3. **消费边界**：读取 Python 不增加同步；读取 notebook、配对输出及执行 shell 时，消费者启动前同步已完成；编辑与执行交替时正确分段。
4. **生命周期**：正常批末进入下一步骤或结束回合前完成同步；写入后报错、取消均尝试有界收尾，下一批次不会越过未完成清理。
5. **错误反馈**：同步失败阻止依赖操作，诊断包含未完成同步的路径，原程序错误保留，状态不泄漏到下一批次。
6. **既有行为**：直接编辑 notebook 仍被拒绝，无配对文件仍快速跳过，单次编辑正常同步。
7. **性能验证**：用同一代表性 notebook 对比逐次策略与归集策略，记录进程数、整段耗时及输出体积；以重复工作减少为验收目标，不承诺固定提速倍数。

## 后果与部署

应先核实目标 DSH 版本与接口并更新依据，再确认是否实施。决定实施后，将状态更新为“已接受”，再开始实现。

连续编辑不再反复支付同一 notebook 的同步成本。插件需要维护少量批次状态，编辑段内 notebook 的实时可见性有所延迟。

实施涉及 j-cli DSH 源插件、setup 生成流程和聚焦宿主测试。完成验证后，通过既有安装范围内的 `j-cli setup dsh --only hook` 更新集成并重载宿主；不手工修改生成文件或已安装副本。
